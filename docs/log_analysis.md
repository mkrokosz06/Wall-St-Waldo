# Trade Bot — forensic log analysis

Sources: `app/bot.log` (6.4 MB) + `bot.log` (47 MB, repo root), merged and de-duplicated
by `(timestamp, level, message)`. 163,021 timestamped records, 2026-03-18 → 2026-07-07,
25 distinct days with at least one entry fill.

Ledger: **189 exit records / 184 matched round-trips**, `docs/trades.csv`.
Generated by `tools/mine_trades.py`; all tables below by `tools/analyze_trades.py`.

**Provenance of the ledger** — the dashboard parser (`app/trade_log_parser.py`) recovers
exactly the 100 trades whose exit line carries a symbol. This analysis adds **87 trades
the parser silently drops** (74 resolved because exactly one position was open, 13 by FIFO
when several were, 2 unresolvable). Recovered trades are almost all from the legacy era and
net roughly flat, so the headline P&L barely moves (+$157.49 → **+$158.43**), but the
*sample size for every conditional statistic nearly doubles*.

**Sample-size warning, stated once and applying everywhere below:** 184 trades is small and
the P&L distribution is violently fat-tailed. The bootstrap 95% CI on overall expectancy is
**[-$0.02, +$1.89] per trade** — it straddles zero. Only three claims in this document clear
statistical noise (trend-break, hard stop, and the overnight/intraday split). Everything else
is directional evidence, not proof, and is flagged as such.

---

## Findings that matter

1. **The entire profit is 11 accidental overnight/multi-day holds; the intraday strategy is
   flat.** 173 trades that opened and closed the same day made **+$22.79 total ($0.13/trade,
   PF 1.18, bootstrap CI [-$0.29, +$0.57])**. The 11 trades held across a session boundary
   made **+$135.64** — 86% of all P&L, on 6% of the trades. This is not strategy, it is the
   bot being killed before 15:55 (89 `Bot starting` lines vs only 21 `End-of-day cutoff`
   firings). Fix the code path, not the knob: `_should_end_of_day_exit` / `end_of_day_flat_minutes`
   only works while the process is alive — the shutdown path (`stop_bot.py`, `Max runtime
   reached`) must force a flatten, and `_reconcile_on_start` must flatten (or explicitly
   accept) any leg carried across a date boundary. Right now the "edge" is unmanaged
   overnight gap risk on 3x leveraged ETFs; the worst such hold lost **-$19.92 in one gap**,
   2.4% of notional, four times the 0.6% stop.

2. **`enable_trend_break_exit` is the single worst rule and it fires on 58% of all trades.**
   107 trend-break exits: **-$32.26, 22% win rate, expectancy -$0.301/trade, bootstrap CI
   [-$0.43, -$0.17]** — the only exit reason whose CI is entirely below zero. Median hold
   before a trend-break exit is 5.1 minutes; 53 of them were cut inside 5 minutes for
   -$15.21. The config comment already suspects this. The `trend_break_skip_if_profitable`
   escape hatch is set to `trend_break_min_profit_pct_to_skip = 0.0`, which only spares
   trades already in the green *at that instant* — in the leveraged era it spared none
   (12/12 trend-break exits were losses, -$14.67). **Turn `ENABLE_TREND_BREAK_EXIT=false`,
   or raise `TREND_BREAK_CONFIRM_BARS` well above 3 and `MIN_HOLD_MINUTES_BEFORE_STRUCTURE_EXIT`
   well above 2, and re-measure.** Naively removing it recovers ~$32 (+20% of headline P&L),
   though the counterfactual is unknowable from logs alone — those positions would have gone
   on to hit a stop or a target instead.

3. **The 0.6% stop on 3x ETFs is a -$78 line item and it is the largest loss bucket.**
   21 `hard_stop_synthetic` exits: **-$78.32, 14% win rate, expectancy -$3.73/trade, CI
   [-$5.37, -$1.94]**. All 21 are in the leveraged era. Realised loss averages **-0.72% of
   notional against a 0.6% stop**, i.e. ~0.12% slippage per stop-out because the stop is a
   *synthetic market sell*, not a resting broker stop (Alpaca rejects stops on fractional
   positions — `use_notional_market_entry` forces fractional fills). `stop_loss_pct = 0.006`
   is ~2σ of a 1-minute TQQQ/SOXS bar; on the legacy 1x universe the same rule was never hit.
   Either widen `STOP_LOSS_PCT` for the leveraged universe or size to whole shares so a real
   broker stop can rest.

4. **The training loops are a random walk over a knob that decides almost nothing.** 212
   knob-change events. `entry_score_threshold` moved up 56 times and down 46 times
   (109 no-ops) — indistinguishable from a coin flip — and every value it ever took lies in
   **[-0.00255, -0.00025]**, i.e. it never once went *above* the 0.0 config default; the
   nudger only ever loosened. Meanwhile the score gate rejects **1.1%** of scanned candidates
   (19 of 1,706 diagnostic rejections) while the spread gate rejects **31.6%**. The next trade
   after a "loosen" nudge earned **$0.140** and after a "tighten" nudge **$0.728** — the wrong
   sign versus intent, with CIs [-$0.38, $0.71] and [-$0.05, $1.85] that overlap completely.
   **Set `ENABLE_OFFLINE_TRAINING=false` and `ENABLE_ONLINE_TRAINING=false`.** They add a
   moving target that makes every other measurement non-reproducible, for no measurable gain.
   (See the dedicated section below for the mechanical reason this can never work.)

5. **637 entry orders were rejected outright by sub-penny limit prices, and 809 stop
   placements failed.** `invalid limit_price ... sub-penny increment` 422s: 644 occurrences,
   **all in March 2026** — fixed by the later `_quantize_limit_price`. `Failed placing
   stop-loss (SAFE STOP)` : 809, **803 of them in April 2026** — 444 `fractional orders cannot
   be sold short`, 363 `insufficient qty available`. Each of those set `halt_new_entries=True`,
   and `halt_new_entries` was the pre-scan blocker on 56 diagnostic lines. Both classes are
   fixed in current code (quantisation + synthetic stop), but 20 `potential wash trade
   detected` rejections persist and the `insufficient qty` family indicates the bot still
   asks to sell shares already held for another open order. Worth a guard in
   `_place_stop_sell_at_price`.

6. **The bot spends most of its life unable to evaluate anything: 13,535 `Market data stale`
   skips.** `Market data stale ... newest bar is 55-68s old (limit=20s)` was the pre-scan
   blocker on **724 of 964** entry-diagnostic lines (75%). The historical runs used a 20s
   limit against an Alpaca IEX feed that is routinely a minute behind; `stale_data_max_age_sec`
   now defaults to 90, which is the right call, but nothing in the log confirms the new value
   in production. Verify `STALE_DATA_MAX_AGE_SEC` in `app/.env`; at 20s the bot was effectively
   offline for three quarters of its scanning time.

n=184. min 0.2 min, p25 2.1, **median 7.1**, p75 25.2, p90 78.4, max 5,899 min (4.1 days).

| 45–120 min | 8 | +40.77 | 100% | 5.096 |
| >120 min | 17 | +127.65 | 53% | 7.509 |

Median hold: **winners 10.3 min, losers 6.2 min.** So the bot is *not* cutting winners short
relative to losers on average — but everything under 20 minutes is a net loss bucket
(-$48.47 over 131 trades) and everything over 20 minutes is a net gain (+$206.90 over 53).

minutes, collectively -$19.80, and 53 of those closures were trend-break exits.

Caveat: this is *conditional on the exit rule that fired*, so it is partly a restatement of
finding 2 (trend-break exits are short and lossy) rather than independent evidence that
duration itself is causal. The >120 min bucket is contaminated by the 11 overnight holds.

## 6. The training loops — why they cannot work

Mechanics from `app/offline_trainer.py` and `TradeBot._apply_online_training_from_window` /
`_online_nudge_from_trade`:

- Both compute `_ewa(recent exit P&L)` and then set the knob to
  `config_default ± one fixed step`. **The output is a three-valued function**:
  `default - step`, `default + step`, or (online only, inside the ±$0.05 neutral band)
  `None`. It does not accumulate, so it cannot converge on anything; it just toggles.
- Offline and online write to the *same* two state fields (`dynamic_entry_score_threshold`,
  `dynamic_min_momentum_return`) with *different* step sizes (0.00025 vs 0.00015) and
  different lookbacks (50 trades vs EWA-50). Whichever ran last wins. 97 offline events,
  115 online events in the log — they overwrite each other continuously.
- `offline_trainer._PNL_RE` matches `exit_pnl=` on **any** log line and does no
  entry-matching at all, so its training window includes the 4 zero-P&L phantom exits and the
  5 orphan exits that have no corresponding entry. It also re-reads the whole file on every
  process start (89 starts in this history), which is why a single unchanged log produced 97
  separate `Offline training applied` events. The training input is a noisier superset of the
  ledger in this document.

Observed behaviour:

- 212 knob-change events. Score threshold: **56 increases, 46 decreases, 109 no-change**.
  A fair coin gives 51/51. This is a random walk.
- Every value ever written is negative: `score_th ∈ [-0.00255, -0.00025]`,
  `mom_th ∈ [-0.00255, -0.00025]`, against config defaults of 0.0 for both. The loop's net
  effect over four months was to *permanently loosen* both gates — including
  `min_momentum_return` going negative, i.e. **buying dips**, which the config's own comment
  (`offline_training_min_min_momentum_return = -0.002 # prevent drifting back to buying dips`)
  says is undesirable. The clamp floor was doing real work and the loop sat against it.
- Predictive value of a nudge on the very next trade:

  | nudge direction | n | expectancy of next trade | win% | 95% CI |
  |---|---|---|---|---|
  | loosen (recent P&L positive) | 113 | $0.140 | 37% | [-$0.38, +$0.71] |
  | tighten (recent P&L negative) | 99 | $0.728 | 25% | [-$0.05, +$1.85] |

  Both CIs contain zero and overlap each other. The point estimates run **opposite** to the
  loop's intent (tightening after losses was followed by better trades than loosening after
  wins), which is what you expect from mean reversion in noise, not from learning.
- Leverage of the knob is negligible anyway: the score gate accounts for **1.1%** of
  candidate rejections (table below).

**Verdict: the prior is correct. Both loops are fitting noise.** Disable
`ENABLE_OFFLINE_TRAINING` and `ENABLE_ONLINE_TRAINING`. Beyond adding no value, they make
the bot non-stationary, which is why any backtest of a fixed parameter set will not
reproduce this log.

## 7. Why the bot did not buy

964 `Entry diagnostic` lines.

Pre-scan blockers (the bot never even scored the universe):

| blocker | count | share |
|---|---|---|
| Market data stale — newest bar too old | 724 | 75.1% |
| `halt_new_entries=True` | 56 | 5.8% |
| `max_open_positions` reached | 2 | 0.2% |

Per-candidate rejection reasons (1,706 tokens across those lines; up to 4 candidates logged
per line):

| reason | count | share | knob |
|---|---|---|---|
| spread too wide | 539 | **31.6%** | `MAX_SPREAD_PCT` = 0.001 |
| already held | 483 | 28.3% | `MAX_OPEN_POSITIONS` |
| momentum below threshold | 360 | 21.1% | `MIN_MOMENTUM_RETURN` (+ trainer) |
| passed all filters | 186 | 10.9% | — |
| per-symbol cooldown | 66 | 3.9% | `ENTRY_COOLDOWN_SEC` = 180 |
| dual-MA not uptrend | 53 | 3.1% | `ENABLE_TREND_FILTER` |
| **score below threshold** | **19** | **1.1%** | `ENTRY_SCORE_THRESHOLD` (+ trainer) |

**The single most selective filter is `max_spread_pct = 0.001`**, rejecting nearly a third of
candidates — plausible on UVXY and SOXS, whose books are wider than 10 bps for much of the
day. And **the filter the training loops spend all their effort tuning is the least selective
one, at 1.1%.**

## 8. Errors and operational failures

163,021 records: 2,567 INFO, ~14,100 WARNING in `app/bot.log` plus ~152,000 WARNING in the
root log, 2,361 ERROR.

| class | count | window | status |
|---|---|---|---|
| `Clock fetch failed ... 401` | 144,145 | Mar 19 – Apr 3 | dead credentials; the root 47 MB log is 97% this one line |
| `Market data stale` skip | 13,535 | Apr – Jul | live; blocked 75% of entry scans |
| `Failed placing stop-loss (SAFE STOP)` | 809 | 803 in April | 444 "fractional orders cannot be sold short", 363 "insufficient qty available"; each set `halt_new_entries=True` |
| `invalid limit_price ... sub-penny` 422 | 644 | all March | fixed by `_quantize_limit_price` |
| `Unhandled error in main loop: <html>` (401) | 852 | Mar–Apr | credential outage |
| `potential wash trade detected` 403 | 20 | Apr–Jul | **still live** |
| `client_order_id must be unique` 422 | 3 | — | benign |
| duplicate/overwritten `ENTRY filled` records | 26 | mostly 2026-03-20 | see below |
| exits with no matching entry | 5 | — | restart artefacts |
| position still open at end of log | 1 (SQQQ) | 2026-07-07 | — |

Bugs visible in the log that cost money or trades:

- **Missing shutdown flatten (costs risk, not yet dollars).** 89 `Bot starting` vs 21
  `End-of-day cutoff` firings, and 11 positions carried across a date boundary — one for
  4.1 days. Net that was +$135.64 of luck; the same mechanism produced the worst single
  trade in the history (-$19.92, -2.4%, four times the intended stop).
- **Duplicate entry fills.** On 2026-03-20 11:06–11:11 the log records seven `ENTRY filled:
  symbol=SPY` lines within five minutes with no intervening exit (26 such overwritten records
  overall). Whatever produced that — reconcile racing the fill handler — means position size
  and the ledger cannot both be right for those trades.
- **`SAFE STOP` failure escalates to a global halt.** `_open_leg`/reconcile set
  `halt_new_entries = True` when a stop cannot be placed. In April this fired 803 times on a
  condition (fractional position) that is now *expected* behaviour and is handled by the
  synthetic stop. Any residual path that still halts the whole bot for a per-symbol stop
  failure is a missed-trade generator.
- **Zero-P&L phantom exits.** 4 records where `_execute_market_exit` logs `EXIT filled` with
  `exit_pnl=0.00` because the position was already gone and the accumulator was empty. These
  pollute the training window and the dashboard win rate.
- **The 47 MB root `bot.log` is 97% a single repeated 401 warning** and contributes only 7
  extra `ENTRY filled` records (2026-03-20 SPY, no matching exits) and zero extra closed
  trades. It can be deleted. The real recovered history was hiding inside `app/bot.log`
  itself, in the legacy `EXIT filled. exit_pnl=` format the dashboard parser cannot read.

## What the data does not support

- Any per-symbol edge. Every symbol with more than four trades has a CI containing zero.
  UVXY (n=4) and DIA (n=2) exclude zero only because a bootstrap over two-to-four points is
  degenerate — ignore them.
- Any claim about the open delay, the SPY market filter, or the candlestick exit — 0, 0 and 1
  observations respectively.
- The claim that 3x leveraged ETFs improved the strategy. CIs overlap; regime and code differ.
- The claim that the bot is profitable. `P(total > 0)` is 0.973 on the raw ledger but only
  **0.731** once the unintended overnight holds are removed — and the overnight holds are a
  bug, not a strategy, so 0.731 is the honest number.
- Time-of-day effects. Every half-hour bucket has n ≤ 30.
- Anything about slippage, fees, or fill quality: `fee_estimate_per_order = 0.0` and exit
  prices in `docs/trades.csv` are *derived* (`entry_price + pnl/qty`), not logged.

## Reproducing

```
python tools/mine_trades.py                 # -> docs/trades.csv  (189 rows)
python tools/analyze_trades.py              # -> every table above
```

`tools/mine_trades.py` is the reusable ledger builder. It merges any number of logs, understands
both log-format eras, recovers the true exit reason from the trigger line preceding each fill,
and marks how each trade's symbol was determined (`symbol_resolved`: `logged` /
`inferred_single_open` / `inferred_fifo` / `unknown`) so downstream work can filter to
high-confidence rows. `tools/analyze_trades.py` imports it and prints the statistics, including
the bootstraps.

`docs/trades.csv` columns: `entry_ts, exit_ts, symbol, qty, entry_price, exit_price, pnl,
hold_sec, hold_min, exit_reason, trailed, entry_score, era, symbol_resolved`. Timestamps are
America/New_York (verified against the 15:55 end-of-day flatten). `exit_price` is derived, not
logged. `trailed` counts trailing-stop raises observed while the position was open.
